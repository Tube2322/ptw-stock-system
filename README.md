# PTW STOCK SYSTEM

ระบบบริหารจัดการสต็อกวัสดุสำหรับโรงพยาบาล (Hospital Material Stock Management) — รับเข้า / เบิกจ่าย / ติดตามสถานะ / วิเคราะห์ต้นทุนวัสดุเทียบตัวชี้วัดการให้บริการ (OPD/IPD)

**Production:** https://ptw-stock-system-shonseys-projects.vercel.app

## สถาปัตยกรรม

โปรเจกต์นี้เป็น **Single-file Static SPA** ไม่มีขั้นตอน build/compile:

- **Frontend:** `index.html` ไฟล์เดียว (HTML+CSS+Vanilla JS ทั้งหมด ~1,150 บรรทัด) ไม่ใช้ framework, ไม่มี bundler
- **Backend:** [Supabase](https://supabase.com) — Postgres + Auth + Row Level Security (RLS) + RPC (Postgres Functions)
- **Hosting:** Vercel (static hosting, auto-deploy จาก GitHub `main` branch ทุกครั้งที่ push)
- **ไม่มี:** build step, bundler, package manager, unit/integration/E2E test suite, CI pipeline, staging environment

ทุก business logic ที่กระทบข้อมูล (ตัดสต็อก, สร้างเลขที่เอกสาร, ลบข้อมูลย้อนหลัง ฯลฯ) อยู่ใน Postgres Function (`SECURITY DEFINER`) ฝั่ง Supabase ไม่ใช่ฝั่ง client — client เรียกผ่าน `sbClient.rpc(...)` เท่านั้น เพื่อป้องกันไม่ให้ผู้ใช้ปลอมแปลงค่าจากฝั่ง browser

## Roles

ระบบมี 2 สิทธิ์การใช้งาน (บังคับด้วย DB constraint `profiles_role_check` และ `fn_admin_set_role`):

| Role | สิทธิ์ |
|---|---|
| `all` (ผู้ดูแลระบบ) | ใช้งานได้ทุกหน้า ทุกฟังก์ชัน รวมถึงจัดการผู้ใช้/รีเซ็ตข้อมูล/ลบข้อมูลย้อนหลัง |
| `viewer` (ผู้ชม) | อ่านอย่างเดียว — เห็น Dashboard, สินค้าคงคลัง, ประวัติเคลื่อนไหว, ตั้งค่าบัญชีของตัวเอง |

สมัครสมาชิกใหม่ (self-signup) จะได้สิทธิ์ `viewer` เป็นค่าเริ่มต้นเสมอ (ผ่าน DB trigger `handle_new_user`) ต้องรอผู้ดูแลระบบเลื่อนสิทธิ์ให้ในหน้า **ตั้งค่าบัญชี → จัดการผู้ใช้งานและสิทธิ์**

## จุดเข้าใช้งานสำหรับผู้เบิก (QR Kiosk Mode)

การเข้าที่ URL พร้อม `#req` (เช่นจากการสแกน QR ในหน้า "ทำใบเบิก") จะเปิด **Kiosk Mode**:

- ถ้ายังไม่ได้ login → ข้ามหน้า login ไปเลย เข้าฟอร์ม "ทำใบเบิก" ได้ทันทีแบบไม่ต้องมีบัญชี (anonymous) — ผู้กรอกมีหน้าที่กรอกข้อมูลอย่างเดียว ไม่ต้องเก็บ/ยืนยันตัวตนใดๆ
- UI ถูกปรับให้เหมาะกับมือถือ: ซ่อน sidebar และปุ่มที่ไม่เกี่ยวข้อง เหลือแถบด้านบนแถบเดียว
- RLS เปิดสิทธิ์อ่าน (`select`) ให้ผู้ใช้ anon เฉพาะตาราง `departments` และ `products` เท่านั้น (ตารางอื่นยังคงต้อง login)

## ⚠️ พฤติกรรมจริงของ "ใบเบิก" (สำคัญ)

**ทุกใบเบิกที่บันทึกผ่านฟอร์ม "ทำใบเบิก" (ทั้งจากผู้ใช้ที่ login และจาก QR kiosk แบบไม่ login) จะถูก "ตัดสต็อกทันที" และตั้งสถานะเป็น "จ่ายแล้ว" ในขั้นตอนเดียว** — ไม่มีการหยุดรอตรวจสอบ/อนุมัติก่อน (ดูรายละเอียดใน `fn_save_requisition`)

หน้า **"ตรวจสอบใบเบิก"** และ **"จ่ายออก"** (ส่วน "รอจ่ายออก") ยังคงอยู่ในเมนู และ RPC เบื้องหลัง (`fn_approve_requisition` / `fn_reject_requisition` / `fn_issue_requisition`) ยังทำงานถูกต้องหากถูกเรียกใช้ — แต่ **ปัจจุบันไม่มีช่องทางใดในระบบที่จะสร้างใบเบิกสถานะ "รอตรวจสอบ" ขึ้นมาใหม่ได้อีก** ดังนั้น 2 หน้านี้จะว่างเปล่าเสมอสำหรับใบเบิกใหม่ (มีเพียงข้อมูลทดสอบเก่าที่ใส่ไว้ตรงๆ ในฐานข้อมูลตั้งแต่ก่อนหน้านี้เท่านั้นที่ยังปรากฏ)

การตัดสินใจว่าจะเปิดใช้ขั้นตอนอนุมัติก่อนตัดสต็อกอีกครั้งหรือไม่ ยังไม่ได้ดำเนินการ — รอ requirement เพิ่มเติมจากผู้ใช้งานจริง (หน่วยงาน)

## แก้ไขจำนวนย้อนหลัง (Admin)

ผู้ดูแลระบบสามารถแก้ไขจำนวน "จ่ายจริง" ของแต่ละรายการในใบเบิกที่มีสถานะ "จ่ายแล้ว" ได้ทีหลัง (เผื่อกรอกผิด) ผ่านปุ่ม "✎ แก้ไข" ในหน้ารายละเอียดใบเบิก — ระบบจะคำนวณส่วนต่างและปรับสต็อกให้อัตโนมัติ พร้อมแสดงค่าก่อน/หลังและผลกระทบต่อสต็อกให้ยืนยันก่อนบันทึกจริง

## ลบข้อมูลย้อนหลังรายเดือน

ผู้ดูแลระบบลบข้อมูล "ใบเบิก / ใบรับ / ประวัติเคลื่อนไหวสต็อก (ledger)" ของเดือนใดเดือนหนึ่งทิ้งถาวรได้ที่ **ตั้งค่าบัญชี → ลบข้อมูลย้อนหลังรายเดือน** — บังคับให้ export CSV ก่อนเสมอ และต้องพิมพ์รหัสผ่านบัญชีจริงยืนยันตัวตน (ตรวจสอบฝั่ง server) ก่อนลบ ข้อมูลที่**ไม่ถูกลบ**: ยอดสต็อกปัจจุบัน, Monthly KPI, สินค้า/หน่วยงาน, บัญชีผู้ใช้ทุกคน

## Database

Supabase project: `ekvjwdistihmkcuquayl` — ตารางหลัก: `products`, `departments`, `requisitions`, `requisition_items`, `receives`, `stock_transactions` (ledger), `monthly_kpi`, `profiles`, `flow_log`

Postgres Functions (ทั้งหมด `SECURITY DEFINER`, bypass RLS ภายใน แต่มีการเช็คสิทธิ์เองในตัวฟังก์ชัน):

- `fn_save_requisition` — บันทึกใบเบิก + ตัดสต็อกทันที (validate: จำนวน>0, มีสินค้าพอ)
- `fn_save_receive` — บันทึกใบรับเข้า + เพิ่มสต็อก (validate: จำนวน>0, ราคาไม่ติดลบ)
- `fn_approve_requisition` / `fn_reject_requisition` / `fn_issue_requisition` — ขั้นตอนอนุมัติ/จ่ายออกแบบเดิม (ยังทำงานได้ แต่ปัจจุบันไม่มีทางเข้าถึงจาก UI ตามที่อธิบายด้านบน)
- `fn_admin_edit_requisition_item` — แก้ไขจำนวนจ่ายจริงย้อนหลัง (admin only)
- `fn_admin_set_role` — ปรับสิทธิ์ผู้ใช้ (admin only, จำกัดค่าเป็น `all`/`viewer`)
- `fn_admin_reset_data` / `fn_admin_purge_month` — ล้างข้อมูลทั้งหมด / ลบข้อมูลย้อนหลังรายเดือน (admin only + ยืนยันรหัสผ่านสำหรับ purge)
- `fn_post_tx` / `fn_next_no` — internal helpers (ลงบัญชี ledger, ออกเลขที่เอกสาร)

RLS เปิดใช้งานทุกตาราง — สิทธิ์เขียนทั้งหมดจำกัดเฉพาะผู้ใช้ที่ login และไม่ใช่ `viewer` (`not is_viewer()`) ยกเว้น `stock_transactions` ที่ปิดการ insert ตรงจาก client ทั้งหมด (ต้องผ่าน `fn_post_tx` เท่านั้น) และ `departments`/`products` ที่เปิด `select` ให้ผู้ใช้ `anon` เพื่อรองรับฟอร์ม kiosk

## Known Issues / ข้อจำกัดที่ทราบอยู่แล้ว

ดูรายละเอียดและหลักฐานทั้งหมดในรายงาน QA/QC ล่าสุด (ส่งในแชทกับผู้ดูแลระบบ) สรุปประเด็นหลักที่ยังไม่แก้:

1. **ไม่มี foreign key ป้องกันการลบสินค้าที่มีประวัติเคลื่อนไหวแล้ว** ระดับฐานข้อมูล — ฝั่ง client มีปุ่ม "ลบ" ที่เช็คไม่ให้ลบถ้ามีประวัติ แต่เป็นการเช็คฝั่ง JavaScript เท่านั้น เรียก API ตรงก็ข้ามได้ ทำให้ข้อมูลกำพร้า (orphan) ในตาราง `requisition_items`/`stock_transactions`/`receives` ได้
2. **`fn_admin_set_role` ไม่ป้องกันแอดมินเปลี่ยนสิทธิ์ตัวเอง** ฝั่ง server (UI ปิดปุ่มไว้เท่านั้น) — ถ้าเกิดขึ้นกับแอดมินคนเดียวที่มีอยู่ ระบบจะไม่มีใครใช้ฟังก์ชันแอดมินได้อีกจนกว่าจะแก้ไขตรงฐานข้อมูลโดยตรง
3. ไม่มีการตรวจจับ/แจ้งเตือนเมื่อ session หมดอายุ — ผู้ใช้จะเห็นหน้าจอเดิมค้างอยู่จนกว่าจะกดปุ่มแล้วเจอ error ทั่วไป แทนที่จะถูกพากลับไปหน้า login อัตโนมัติ
4. ข้อความ UI บางจุด ("ตัดสต็อกอัตโนมัติทันที") เป็นการอธิบายพฤติกรรมจริงที่ถูกต้องแล้ว (ดูหัวข้อด้านบน) — แต่หน้า "ตรวจสอบใบเบิก"/"จ่ายออก" ที่ยังอยู่ในเมนูอาจทำให้เข้าใจผิดว่ามีขั้นตอนอนุมัติ ทั้งที่ปัจจุบันไม่มีทางเข้าถึงได้จริง
